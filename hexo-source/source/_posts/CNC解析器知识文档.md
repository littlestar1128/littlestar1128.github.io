# CNC 解析器知识文档：词法、语法与模态状态

本文沿着一行 G 代码的数据流阅读解析器：字符如何形成 Token，Token 如何形成当前段字段，当前段字段如何结合历史模态得到语义结果，以及结果如何交给刀补和插补。重点对应资料中的 `GetToken`、`match`、`ParseAccidence`、`ParseSyntax` 和 `Interperate`。

补充资料使词法层的认识更具体：记录中的系统存在独立的 `GetToken` 和 `match`，不能只用“逐字符 switch 解析地址字”概括全部实现。配套 C99 学习版采用了较简化的扫描结构，适合验证数据关系；它没有恢复旧系统的宏程序、完整调度器和全部指令。

**使用边界。**三份资料都是历史问答记录，包含截图说明、局部代码、教学改写和推测。本文将它们作为学习线索，不把记录里的“完整提取版”自动认定为完整原源码。所有教学代码均明确标注；不能从字段名直接推定它的单位、坐标系或运行时含义。

阅读顺序：先读第2至5章理解 Token 和字段，再读第7至9章理解模态，最后读第10至14章理解宏程序、坐标边界和工程实现。第6章专门校正补充资料中的编码矛盾，第15章提供来源索引。

## 1 解析器处理的对象

### 一行程序包含多个层次

以 `N10 G01 X100 Z-5 F120` 为例：整行称为程序段或 block；`G01`、`X100` 等是地址字；`G`、`X` 是地址符；`01`、`100` 是数值文本。分词器可以进一步把地址符和数值拆成不同的 Token。因此，地址字和 Token 不一定一一对应。

| 层次 | 本例中的内容 | 要回答的问题 |
| --- | --- | --- |
| 字符 | `G`、`0`、`1` | 当前读到哪个字符 |
| Token | `G`、`NUM("01")` | 这段字符属于什么类别 |
| 当前段字段 | 本行有运动指令，有 X、Z、F | 本行实际写了什么 |
| 语义结果 | 有效运动为 G01，目标位置和进给已确定 | 结合上下文后是什么意思 |
| 输出段 | 几何、模态和辅助事件 | 后续模块需要哪些数据 |

LinuxCNC 官方概览将程序行、地址字与实值区分开，并说明实值可以来自表达式。这可作术语参照，但旧系统支持的语法仍以它自己的实现为准。[W1](#source-w1)

### 词法 语法和语义的区别

词法分析识别文字形式，例如 `X`、数值、`IF` 和比较符。语法分析检查组合结构，例如 X 后是否具有合法的值、IF 后是否具有条件结构。语义分析解释这些结构，例如同一个 S 在 G96 与 G97 下代表不同物理量。

旧工程常把部分语法、数值校验甚至语义处理都放在名为 `ParseAccidence` 或 `ParseSyntax` 的函数中。阅读代码时应按实际职责分类，不要要求函数名称与编译原理术语完全一致。

解析器可以直接输出结构体，不必先建立抽象语法树 AST。是否使用 Token 列表、语法树或直接填充字段，是实现选择；资料中的函数名本身不能证明存在 AST。

## 2 从输入文本到输出段

资料展示的正常处理路径可以概括如下。宏程序、循环展开、MDI 和重译码会增加分支，因此这张图表示职责关系，不保证每次调用都会完整经过所有步骤。[S3，第2049至2254行、第4157至4313行]

```text
程序文件或 MDI 输入
        ↓
GetNextChar → GetToken → ReservedLookup
                    ↕
             match 与当前 Token
                    ↓
            ParseAccidence
             当前段词法字段
                    ↓
              ParseSyntax ← 已继承的工作模态
               当前段语义结果
                    ↓
              ParseCutter
         坐标变换与补偿后的输出段
                    ↓
             缓冲区与执行层
                    ↓
          预处理 速度规划与周期插补
```

`Interperate` 在外层安排初始化、数据来源、循环展开、语法处理和刀补处理。`Decode_Task` 再根据缓冲区空间等条件反复调用它。返回 `ParseAccidence` 不代表文件已经处理完，更不意味着应该由词法函数自己执行整份程序。

解析关注“这一段要做什么”。插补关注“在一个执行周期中怎样沿轨迹前进”。S 字段的识别、运动段的建立与主轴实际转速计算，是三个可以位于不同层次的工作。

## 3 GetToken 如何识别一个词

### 一个 Token 包含类型和文本

`GetToken` 一次返回一个词法单元。`cur_Token` 保存类别，`tokenString` 保存本次识别的字符文本。例如解析 `X100` 时，可能先返回类型 X、文本 `"X"`，再返回类型 NUM、文本 `"100"`。NUM 是类别，100 才是数值内容。[S3，第170至202行]

对于数字，先保留文本有利于做格式校验和范围检查。下一次 `GetToken` 可能覆盖 `tokenString`，因此需要的值应在推进 Token 之前读取或复制。

### 状态机的职责

状态决定当前字符应该如何解释。每次调用开始时通常从 START 进入；字符游标则必须保持在上次停止的位置，不能每次都回到行首。资料中出现了 START、INADDRESS、INNUM、INPOINT、DONE 等名称，其他细节尚不完整。[S3，第399至458行、第2682至2780行]

| 状态或处理路径 | 常见输入 | 主要动作 |
| --- | --- | --- |
| START | 空白、字母、数字、注释起点 | 选择下一种识别方式 |
| INADDRESS | G、X、SIN、EQ | 累积字母文本，遇到边界完成识别 |
| INNUM | 数字字符 | 累积整数部分，遇小数点转入小数状态 |
| INPOINT | 小数点后的数字 | 累积小数部分，拒绝不允许的格式 |
| 注释处理 | 圆括号或该方言的注释符 | 跳过或记录注释，检查闭合 |
| DONE | 一个词已经完整 | 封口文本，返回 Token 类别 |

负号、前导小数点、变量符、逻辑符的具体状态组合需要继续核对实现。例如 `-12` 可以由扫描器返回一个有符号数字，也可以由上层把负号 Token 与数字组合；不能由上述简表认定旧系统必然采用其中一种。

### 为什么需要回退一个字符

扫描 `123X` 时，读到 X 才知道数字结束。X 属于下一个词，不能丢掉。资料里的 `UnGetNextChar` 用来把边界字符退回，让下次 `GetToken` 再读取它。完成地址符 X、准备读取后面的数字时，也可能使用同样的机制。

```text
输入       1 2 3 X 4
本次读取   └─数字─┘ ↑ 发现数字结束
返回       NUM("123")
下次读取         从 X 开始
```

回退必须有明确的次数和边界。读完文件后反复回退 EOF，或者未推进游标就再次请求同一个词，都可能导致死循环。正常路径应推进输入、结束当前词、切换输入来源或明确报错。

### ReservedLookup 的作用

读取一串字母后，`ReservedLookup` 根据文本查表，决定它是 X、G、SIN、IF、EQ 等哪个 Token。它负责识别名称，不负责计算函数或执行分支。识别到 SIN，并不能证明后续已正确实现角度单位、参数范围和运算错误处理。

资料对符号 `$` 等存在带问号的说明；这类内容只能列为待核实，不能据此定义系统变量语法。

## 4 match 如何推进当前 Token

### 核心约定

在常见的单 Token 前瞻解析器中，`match(expected)` 先检查当前 Token 是否为 expected；匹配成功后才调用 `GetToken` 取得下一个。补充资料的不同段落对此有相反表述，阅读时应采用这一明确约定，并以真正的函数体最终核实。[S3，第2085至2089行；对照第1124至1128行]

以下是教学伪代码，错误返回类型和状态对象并非旧接口：

```c
bool match(Parser *p, TokenKind expected)
{
    if (p->current.kind != expected)
        return report_expected_token(p, expected);

    p->current = GetToken(p);
    return true;
}
```

### 按步骤读取 N10 G01

| 当前 Token | 上层操作 | 操作后的当前 Token |
| --- | --- | --- |
| N | `match(N)` | NUM，文本为 `10` |
| NUM | 读取文本，转换并校验 N 值 | 仍然是这个 NUM |
| NUM | `match(NUM)` | G |
| G | `match(G)` | NUM，文本为 `01` |
| NUM | 读取并解释 G 值，再 `match(NUM)` | 下一 Token 或 ENDLINE |

这样，一个 `case N` 通常消费地址 N 和它后面的值，而不会连带丢掉后面的 G。读到 X100 后进入 `case Z`，也是通过 Token 推进和外层循环完成的，不需要 X 分支主动跳转到 Z 分支。

最常见的错误是提前 `match(NUM)`，然后才读取已被覆盖的 `tokenString`；另一个错误是分支里已经推进一次，外层又无条件推进一次，导致漏词。调试时必须同时观察“当前 Token”和“输入游标”，不能只看其中一个。

<a id="current-block"></a>

## 5 ParseAccidence 如何生成当前段字段

### 地址字解析的常见步骤

以普通 X 字为例：确认地址 X，推进到值；判断值是普通数字、变量还是表达式；得到一个数值或待处理的表达式描述；校验；写入数值字段和存在标志；最后推进到下一地址。N、G、X 各分支的约束不同，不能共用“读一个 double 就结束”的逻辑。

补充资料转写中出现 `Nnum`、`Xnum` 等计数器，可用于发现重复地址；出现 `ComputePosVal`、`BracketString`、`VAR`、`LBRACKET`，表明这里还承担了值的组织工作。完整调用链不在资料中，因此不能认定所有表达式都恰在词法阶段求值。[S3，第198至209行、第2188至2254行]

### 数值和存在标志必须分离

| 输入状态 | 数值字段可能是什么 | 存在标志表达的含义 |
| --- | --- | --- |
| 写了 `X0` | 0 | 本行明确指定 X |
| 没有写 X | 0 或初始化残留值 | 本行没有 X 字 |
| 写了 `S0` | 0 | 本行明确指定 S |
| 没有写 S | 旧缓存或默认值 | 本行没有显式 S 更新 |

不能写 `if (Xvalue != 0)` 来判断是否有 X，也不能用 `SCode > 0` 代替“本行写了 S”。数值合法性是另外一层规则，例如一个控制系统可以允许普通 S0，却要求最高转速限制必须为正数。

### 数字从文本到数值

整数的十进制累积可写为 `value = value * 10 + digit`。小数部分逐位乘 0.1、0.01 等权重。有符号数字还需要单独处理正负号。`X-12.34` 的数值最终为 -12.34，而不是先将 12 与 0.34 分别做相互抵消。

使用 `strtod` 等标准函数时，应检查是否真正读入数字、是否消费完整预期文本、是否发生范围错误，以及结果是否有限。仅调用 `atof` 无法可靠区分非法文本与合法的 0；扫描器的严格格式检查不能被省略。

### N 行号校验的准确含义

补充资料的 N 分支转写要求数值为整数、范围为 0至999999，并拒绝变量引用。比较 `tmpCode != (long)tmpCode` 检查的是数值是否有非整数部分；如果前端允许相应数字文本，`10.0` 数值上仍是整数。因此，不应把这条比较直接解释为“文本里绝对不能有小数点”。[S3，第2085至2127行]

实现时应先确认有限性与可表示范围，再进行浮点到整数的强制转换，避免超范围转换。更大的经验是：地址约束属于具体方言。LinuxCNC 官方手册对 N 的文字格式另有规定，不能把一套控制器的 N 规则推广到全部系统。[W1，Line Number](#source-w1)

## 6 G 代码编号 分组与内部编码

### 三种编号不能混淆

`G96` 是程序中的命令名称；`Gcode[2]` 的 2 可以是当前实现内部的分组槽位；696 则可能是某套实现对 G96 使用的整数编码。三者不处在同一个层次。数组下标 2 也不表示“本行第二个 G 字”。

旧片段支持按 `Gcode[1]` 处理运动、按 `Gcode[2]` 判断 G96/G97、按 `Gcode[9]` 处理固定循环。更完整的分组表和所有常量定义缺失。配套 C99 学习版自行定义了 `CNC_GGroup`，其中部分编号不能当成旧系统的分组表。[S1，第2863至2869行截图；S2，第27659至27704行]

### 补充资料中的公式为何不能直接采用

补充资料前部同时给出 `整数部分 * 100 + 小数部分 * 10 + 600` 和 G01→601；后部又给出 G01→700，并承认是教学演示。这些说法不构成一套一致编码。[S3，第38至50行、第1241至1255行、第1549至1566行]

| 假设或例子 | 实际算术结果 | 能得出的结论 |
| --- | --- | --- |
| 整数 G 值加 600 | G01→601，G96→696 | 与部分记录相容，不能据此推广小数 G 码 |
| `1 * 100 + 600` | 700 | 与 G01→601 冲突 |
| `90 * 100 + 1 * 10 + 600` | 9610 | 不是前文表中的 6910 |
| 小数 G 值由 `G_stmt_f` 处理 | 具体 ID 未知 | 需要小数白名单和映射表证据 |

正确阅读顺序是：先看数值识别，再看 `G_stmt` 或 `G_stmt_f` 的映射，最后看常量定义和下游 `switch`。如果只看到下游与 696 比较，可以记录“该路径把 696 当作某状态”，但不能反推全部指令的统一编码公式。

补充资料更靠近截图的解释区分了整数 G 码和小数 G 码白名单，提到了 `G_stmt_f` 与 `G_stmt`。这比前部通用公式更有参考价值，但它仍是问答转写，不等于原始函数完整定义。[S3，第2134至2184行]

### 小数 G 码的校验

G90.1 是命令编号的一部分，不是一个可以任意近似的坐标。实现可以用“整数部分加扩展号”、规范化字符串或受控的数值映射识别它；旧资料也展示了按 `FloatMin` 做白名单比较的思路。若采用容差，必须清楚边界，避免把不支持的 G1.0001 静默当成 G1。

### 分组必须防止覆盖丢失

如果每个组只保留一个槽位，新 G 字写入前就要检查该槽是否已有值，或另存出现次数。否则 `G00 G01` 的后一个值覆盖前一个，语法层将看不到冲突。检查具体放在 `G_stmt` 还是 `ParseSyntax` 是工程选择，不能断言词法函数绝不做分组合法性检查。

## 7 ParseSyntax 如何确定有效语义

### 以当前段和旧模态共同解释

语法处理一般要完成指令组合检查、参数解释、有效模态计算以及当前段事件生成。对于运动，至少要知道当前运动模式、坐标模式、平面和本行轴字；对于 S，还需要当前主轴速度模式。

同组互斥与跨组互斥不同。G00 和 G01 属于相互竞争的运动模式；某系统禁止 G96 与极坐标模式同时启用，则是跨组的业务约束。不同控制器的组号和业务约束需要分别核对。LinuxCNC 的“同组不能在一行同时出现”可作分组概念参照。[W1，Repeated Items 与 Modal Groups](#source-w1)

### 模态值与本行显式标志

| 信息 | 例子 | 保存时间 |
| --- | --- | --- |
| 本行显式出现 | `IsSetG96G97Select` | 当前段事件，下一行重新确定 |
| 当前有效模态 | `G96G97Select` | 跨段保持，直到改写或复位 |
| 当前词法字段 | `Sflag`、`Scode` | 当前段扫描结果，可被处理函数消费 |
| 最终输出快照 | `InterpG96G97Select` 等 | 随该输出段保存，供执行阶段使用 |

“没写 G01”通常不等于“没有运动模式”。如果之前的 G01 仍有效，本行的轴字可以继续按 G01 处理。另一方面，“G01 模式有效”本身也不等于每一行都应生成运动段；还需看是否存在运动目标，以及轴字是否已被 G50 等其他指令消费。

### 同行字的书写顺序和语义处理顺序

分词和文本扫描从左到右，不意味着各项语义必须按文本位置立即执行。例如解释 `S200 G96` 时，需要知道同一段中的 G96；直接用遇到 S 时的旧模态解释，就可能出错。解析器通常先收集字段，再按规定的语义顺序处理。LinuxCNC 官方概览同样单列了地址顺序和执行顺序的规则；其他方言应查自己的约定。[W1，Item Order 与 Order of Execution](#source-w1)

对于跨组冲突，还要明确检查“旧状态”“中间状态”还是“本段最终有效状态”。配套学习版采用最终状态检查，因此允许从 G96 状态通过同段 G97 与 G112 切换到不冲突的组合。这是学习版策略，不能认定旧系统必然相同。

## 8 data1 data2 data3 的生命周期

### 角色比名字更重要

| 对象 | 资料中的类型或名称 | 主要职责 |
| --- | --- | --- |
| data1 | `CNC_AccidenceData`，常见变量名 dataInt | 本行出现的字、数值、宏控制信息 |
| data2 | `CNC_SyntaxData`，常见变量名 dataConv | 本行经解释后的语义结果和事件 |
| data3 | `CNC_TmpSaveData`，常见变量名 TempSave | 译码工作模态、计划坐标和中间状态 |
| 持久状态 | `cur_seg_mode` 等 | 为下一段提供已保存的模态依据 |
| 输出段 | `CNC_CodeSegMent` 或记录中的相近拼写 | 补偿后交给后续模块的数据 |

`data2` 不能直接等同于最终输出段；`data3` 也不能直接等同于它内部某个 `TmpModeData` 成员。结构体名字相似，只能说明关联，不能证明布局相同或可以直接互相拷贝。

### 三类初始化需要分别看

系统复位初始化会建立起始模态。当前段初始化会清理本行存在标志和事件。模态继承则把上一段状态复制或重建为本段工作状态。这三件事不能混用；每行清空全部模态会丢失 G01、G90 和 S 等继承信息。[S3，第4051至4070行、第4168至4172行、第4253至4256行]

旧记录有 `InitTmpSaveData` 从 `cur_seg_mode.TmpModeData` 拷贝数据的片段，这是继承关系的证据。完整的回写时机、复位时机和异常回滚策略仍需另查，不能只见到一次 `memcpy` 就推定全部生命周期。[S2，第28001至28009行]

### 消费字段不会自动取消模态

`Sflag = 0` 可以表示本行 S 已处理；`Gcode[group] = -1` 可以表示本组待处理字段已被消费。它们不等于把持久模态 G96 或 G01 取消。数据使用了相同的哨兵值时，应结合“初始化之前还是处理之后”理解。

`ComG00Deal` 的旧片段只有在 `Gcode[1] != -1` 时才赋值 `MoveSelect`。调用这个名字的函数本身，不足以证明它无条件插入 G00 段或向插补队列写入数据。[S2，第27659至27704行]

## 9 两组逐段推演

### 运动与坐标模式的继承

以下为教学推演，约定单位毫米、半径尺度、无偏置和刀补，初始 X=0、Z=0。只讨论几何和模态，不模拟执行时间。

| 程序段 | 本行重要字段 | 解释后的位置与状态 |
| --- | --- | --- |
| `N10 G90 G01 X10 Z5 F100` | G90、G01、X、Z、F | X=10，Z=5；绝对模式，G01，F=100 |
| `N20 X20` | 只有 X | X=20，Z=5；继承 G01、G90、F=100 |
| `N30 G91 Z-2` | G91、Z | X=20，Z=3；按增量修改 Z |
| `N40 G90 X0` | G90、X，且 X 明确为0 | X=0，Z=3；X0 不能被当作没写 |

读 N20 时，词法层只知道本行有 X20；到语义层结合旧模态才知道这是一次 G01 绝对运动。若只查看 `data1`，就无法独立解释整段。

### G96 G97 与 S 的解释

配套学习版明确采用两个缓存：`G96Speed` 保存线速度，`Scode` 保存恒转速目标。旧截图支持 G96 分支依据本行或继承模态解释 S；完整 G97 分支与切换策略没有原代码证明。下面的“省略 S”行为因此标为学习版约定。[S1，第2863至2869行截图；S2，第20235至20258行]

| 程序段 | 学习版的解释结果 | 本行标志 |
| --- | --- | --- |
| `G97 S800` | RPM缓存为800，有效模式G97 | 显式模式，显式S |
| `G96 S200 P1` | 线速缓存为200，有效模式G96 | 显式模式，显式S、P |
| `G01 X40` | 线速缓存仍为200 | 没有显式S |
| `S180` | 继承G96，更新线速缓存为180 | 显式S，没有显式模式 |
| `G97` | 使用保存的RPM缓存800 | 显式模式，没有显式S |
| `G97 S0` | RPM目标更新为0 | 显式S，数值为0 |
| `G50 S1500` | 更新最高转速限制，不改RPM或线速缓存 | 限速事件，不是普通S更新 |

G96 的 S 表示线速度，G97 的 S 表示转速，实际单位还要结合系统单位约定。LinuxCNC 也区分这两种主轴模式，但它自己的参数规则不能直接套入旧系统。[W2，G96 G97](#source-w2)

“G97 不带 S 时继承 G96 当时计算出的 RPM”是另一种可能的产品策略，需要执行层的实际目标转速或反馈信息。纯前端解析器只看文本和静态模态，通常无法知道真实执行瞬间的这个数值。

## 10 宏变量 表达式和控制流

### 变量编号和值不是一回事

`X#100` 需要区分地址 X、变量引用符以及变量编号100，再读取变量表得到 X 的值。`X[#100+2*3]` 还需要处理括号、运算优先级和求值。仅把 `#100` 的数字100当作坐标，会得到完全不同的语义。

表达式的典型处理步骤是：识别 Token，建立表达式结构或转换为后缀表示，执行运算，再做使用场景的范围与单位检查。资料提到 `BracketString`、`in_post` 和 `calculator`，可以沿这条职责线理解，但具体 Token 编码和所有运算规则未完整提供。[S3，第323至350行、第2195至2249行]

下面是教学表达式，假设变量100的值为10：

```text
中缀表达式    #100 + 2 * 3
后缀表示      VAR100 2 3 MUL ADD
数值结果      16
```

后缀计算时，数值入栈，乘法先弹出2和3并压入6，加法再用10和6得到16。变量读取、运算符的元数、除零、函数定义域、栈容量和括号闭合都需要明确处理。识别函数名只是其中最前面的一步。

### 方括号和圆括号可能有不同职责

在资料展示的方言中，方括号用于表达式，圆括号常用于注释。不能把一切括号都删掉，也不能把注释里的 X999 当成真正轴字。括号层数属于需要受控的解析状态，异常输入必须能退出并报错。

### IF GOTO WHILE 需要程序上下文

IF 需要条件结果；THEN 或 GOTO 需要决定执行后续赋值还是改变程序位置；WHILE 与 END 需要循环配对和返回位置。它们已超出一个“地址加数字”的扫描器。

至少需要保存变量环境、文件或程序游标、标签索引、循环栈、子程序返回栈，以及必要的局部作用域。循环编号上限、变量持久性和跳转搜索规则都是具体实现规则，不能根据一条 `DoNum > 3` 检查就断言整个系统最多只有三层所有类型的嵌套。

条件为假时，禁止发生不该发生的赋值或运动是语义要求；是否仍然解析表达式、是否仍会检查求值错误，则需要看实现策略。资料中的 `IfThenFlgCase` 提供了条件控制的线索，不足以证明所有假分支都完全不进入计算器。

宏语法也有方言差别。记录中的大写 IF/GOTO 结构不能直接等同于 LinuxCNC 的 o-code 控制结构，更不能把一套宏程序未经检查交给另一套解析器。

## 11 坐标解释与插补交接

### 先明确位置属于哪个坐标系

对一个仅含平移偏置的教学模型，约定 `M = W + O`，其中 M 是机械坐标，W 是工件坐标，O 是偏置。实际系统还可能有刀偏、旋转、镜像、缩放和极坐标变换，不能把这个简式当成全部机床的完整公式。

旧资料展示了初始化时减偏置、输出时加偏置的片段。这说明同一位置可能在不同阶段用不同坐标系表达。判断错误时，应同时追踪起点、终点和偏置，不能仅看某个加号就决定删除它。[S2，第24818至24902行]

### G50 坐标重定义与运动的区别

以下采用旧记录和学习版中的车床语义，约定半径尺度、无刀补、单轴平移。不同系统上的 G50 含义需要单独核对。

| 步骤 | M机械位置 | W工件位置 | O偏置 | 是否产生运动 |
| --- | --- | --- | --- | --- |
| 初始 | 10 | 10 | 0 | 否 |
| `G50 X100` | 10 | 100 | -90 | 否，只重定义显示位置 |
| `G0 X90` | 0 | 90 | -90 | 是，机械位置移动-10 |
| `G50 S1500` | 0 | 90 | -90 | 否，只设置限速 |

G50 的坐标字已经用于重定义坐标，就不能再被默认运动逻辑重复消费为目标位置。若一行同时写坐标重定义和运动，必须明确轴字归谁使用；学习版拒绝这一歧义组合。

### 起点和终点必须可直接比较

如果机械起点为10、偏置为-90，工件起点应为100。不能用工件起点100直接减机械终点0来推导实际位移。应在同一坐标系下计算，例如机械终点0减机械起点10得到-10。

直径尺度也必须统一。X字为直径100而插补使用半径时，应在规定边界换算为50；起点、终点、相关偏置不能只有一项除以2。I/J/K与R是否跟随轴字倍率，还要查当前方言和接口约定。

G53 是一个有用的核对用例：LinuxCNC 将它定义为非模态机械坐标运动；学习版也将机械坐标覆盖限定在该行。下一行恢复工件坐标解释，但同行显式设置的 G0/G1 是否持续，需要分别看运动模态，不应整体撤销。[W2，G53；S4，CNC_ParseLine与ParseSyntax](#source-w2)

### 计划位置和实测位置要分开

译码器可能预先处理多个尚未执行的段。它维护的“当前机械坐标”可以是译码进度中的计划终点，不一定是编码器此刻反馈的位置。仅见到 `BefComPos`、`curpos` 或 `StartX` 等名称，还不能认定它来自实时测量。

当输出段带着终点和偏置跨越模块边界时，应明确接收方究竟接收工件坐标还是机械坐标，是否还会应用偏置。没有接收方契约或可验证数据流，就不能断言闭源库一定重复叠加了偏置。

## 12 Interperate 与译码任务的调度

### 正常行与展开段

补充资料中的 `Interperate` 转写包括首行初始化、MDI与自动运行处理、循环展开标志、实时信号等待、手轮重译码，以及后续语法与刀补调用。它是调度封装，不只是字符串函数。[S3，第4019至4334行]

固定循环可能从一行程序展开多个运动段；宏循环也可能需要重复访问已有程序位置。因此，一次调用 `Interperate` 不一定读取一个新的文本行，连续返回多个段也不意味着重复扫描发生了错误。

| 运行情形 | 可能使用的数据来源 | 阅读时关注的状态 |
| --- | --- | --- |
| 正常自动译码 | 文件中的下一行 | 文件游标、行结束、缓冲区空间 |
| MDI | 一行或多行输入缓存 | 输入是否为空、模式切换与初始化 |
| 循环展开 | 已保存的指令参数 | 展开阶段、次数、何时恢复读新行 |
| 子程序或跳转 | 程序索引与返回栈 | 调用位置、返回位置、局部环境 |
| 重译码或反向处理 | 保存的历史位置与状态 | 恢复的是哪一段的哪一种状态 |
| 等待实时信号 | 执行层确认或事件 | 是否暂停预读、等待如何解除 |

### 预读与同步点

译码器作为生产者，把输出段送入队列；执行层作为消费者，按自身进度取段。缓冲区满时生产者应等待或暂缓，不能覆盖尚未消费的数据。输出段发布时应保持语义完整，不能让消费者读到半更新的结构体。

有些指令依赖真实执行结果，例如等待外部信号或读取与加工现场有关的反馈。它们可能需要形成同步点，限制继续预读。补充资料中的 `NeedRealTimeSignal` 是这类机制的线索，但 M91、M92 的确切语义属于该系统方言，不是所有 CNC 的通用命令含义。

词法分析里的“前瞻一个 Token”，与轨迹规划中的“前瞻多个运动段”，是两个不同概念。前者解决识别和组合，后者解决运动连续性与速度边界。

### 错误传播需要沿调用链核实

一个处理函数返回 TRUE，可能表示“发生错误”，也可能具有其他约定。`ParseAccidence` 的某个分支调用报警后返回，并不自动证明 `Interperate` 不会继续调用下一层。必须查看调用者如何检查返回值、错误标志及队列发布条件。

补充资料的所谓完整代码仍有省略号和不确定注释，不能由其中缺少一条检查就判定旧系统必然继续执行错误段，也不能反过来保证它已经实现完整回滚。

## 13 错误处理与验证方法

### 把故障定位到最早失真的层

| 现象 | 首先观察 | 常见原因 |
| --- | --- | --- |
| X100 被读成 X10或漏掉Z | 游标、Token文本、match次数 | 边界字符丢失、重复推进、缓冲截断 |
| X0 或 S0 被忽略 | 存在标志和数值分别记录 | 用非零值代替字段存在判断 |
| 只写X时运动模式错误 | 旧模态、有效模态 | 每行误清空模态、继承时机不对 |
| S200 G96 与 G96 S200 不一致 | 字段收集顺序和语义顺序 | 扫描时过早按旧模态处理S |
| G50 产生意外目标 | 轴字消费、段类型、坐标变换 | 轴字重复使用或起终点坐标系混用 |
| 出错后下一行也异常 | 提交前后的状态、队列 | 部分更新提前写入持久状态 |
| 某次调用不读新行 | 循环展开与等待标志 | 可能是正常调度，也可能等待未解除 |

### 推荐记录的观察量

在单行测试入口记录原始行和物理行号；在分词器记录 Token 类型、文本和源位置；在字段收集结束后记录存在标志；在语义层同时记录旧状态和有效状态；在队列发布处记录输出段类型、坐标系、单位以及关键事件。

若有通道号 `chan`，还要确认游标、Token缓冲、变量表和模态各自属于哪个通道。把一部分数组按通道分开，不足以证明其余全局变量也是线程安全的。

### 失败时的状态一致性

一种清晰的学习实现是“复制工作状态，全部通过后一次提交”。以下为教学伪代码；旧系统是否这样实现尚不确定：

```c
candidate = committed_state;
if (!parse_words(line, &words)) return ERROR;
if (!resolve_semantics(&words, &candidate, &result)) return ERROR;
if (!validate_result(&candidate, &result)) return ERROR;
committed_state = candidate;
publish(result);
```

真实工程还要协调队列发布失败、宏变量写入、文件游标和外部副作用。若只回滚一个模态结构，却已改写变量表或移动到另一个子程序位置，仍不构成完整的一致性恢复。

### 有价值的测试用例

| 类别 | 输入或场景 | 预期检查 |
| --- | --- | --- |
| 词法边界 | `G1X0Z-.5`、未闭合注释、缺数字 | 切词正确或明确报错，不静默截断 |
| 重复与分组 | `X0 X1`、`G0 G1` | 发现重复和同组冲突 |
| 数值转换 | 超长数值、非有限数值、N10.5 | 有限性、范围与场景约束 |
| 模态继承 | G1后下一行只有X | 继承运动模式与未更新参数 |
| 事件与缓存 | S0与省略S、G50 S | 存在标志、限速与普通S路由独立 |
| 坐标连续性 | G50重定义后再运动 | 重定义无运动，下一段起点连续 |
| 非模态覆盖 | G53后下一行只写X | 覆盖不泄漏到下一行 |
| 表达式与控制流 | 变量、优先级、假分支赋值 | 与方言规定一致，不产生不该有的副作用 |
| 错误恢复 | 前半段合法、后半段错误 | 本段不发布，已提交状态不被污染 |

圆弧还应测试不可构造的R、圆心格式半径不一致和极小半径。配套学习版曾修正绝对容差误放行极小圆弧的问题；它说明边界测试应验证几何一致性，不能只检查函数返回成功。

### 推荐的学习实践

先手算 `G90 G1 X10 F100` 与下一行 `X20` 的字段和状态，再运行示例比对。然后逐项加入 S0、G96、G50 和 G53，观察本行事件与持久模态的差别。最后再单独设计 Token 层和表达式求值器，避免同时改动所有层而无法定位错误。

每次阅读一个函数，写下四件事：输入是什么，输出是什么，改了哪些持续状态，失败由谁接管。遇到坐标字段，再加上单位和坐标系。这个方法比按文件顺序记所有变量更容易建立稳定理解。
