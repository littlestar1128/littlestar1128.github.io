# RS-422 一主多从：全双工能力、DE 控制与轮询时序

主机向从机1发送请求，等从机1回复结束，再向从机2发送下一条请求。既然数据始终交替传输，为什么还要使用全双工芯片？这不就是半双工吗？

这个疑问的关键，在于区分**链路支持的能力**和**协议实际安排的时序**。严格轮询没有利用上下行同时传输的能力，但它运行的物理链路仍然可以是全双工。另一方面，即使使用全双工收发器，多个从机也不能随意同时驱动同一对回传线。

下面以 MAX1482 构成的四线一主多从网络为例，把接线、地址、DE 控制和轮询流程放在一起说明。

<!-- more -->

> **术语约定：**本文沿用工程中“RS422 一主多从”的常见说法。多个从机驱动器共用一对回传线时，应按四线 RS-485 的多驱动约束设计；严格 RS-422 的每对线上只有一个驱动器。[详见第 6 节](#rs422-rs485)。

## 1. 四线一主多从的线路如何分工

这种网络使用两对差分信号线，一对负责下行，一对负责上行：

- 下行：主机 TX 连接所有从机 RX，只有主机发送，多个从机接收。
- 上行：多个从机 TX 连接主机 RX，多个发送端共享同一对回传线。

![四线一主多从拓扑及主从机 DE 状态](/image/posts/rs422-full-duplex-polling/01-four-wire-topology.svg)

图1中，每条彩色线代表一对差分线。所谓“四线”只统计差分信号线，参考地、屏蔽及隔离设计需要另外考虑；这张图是拓扑示意，不是完整电路图。

两条通道的约束不同。主机独占下行线，其发送驱动可以持续开启；上行线上连接了多个从机发送端，必须保证同一时刻最多只有一个从机驱动，空闲时可以全部关闭。

因此，“从机轮流发送”限制的是上行通道，并没有要求主机在接收期间关闭下行通道。[TI SN65HVD7x 手册第10.2节](https://www.ti.com/document-viewer/sn65hvd73/datasheet)给出了四线全双工主从拓扑，同时要求共享回程上的从机驱动器不能同时开启。

## 2. 有设备地址为什么仍会冲突

所有从机都会从下行线上收到主机发送的比特。帧中的目标地址由各自 MCU 的程序解析，收发器本身不负责判断“这条命令是不是发给我”。

更容易忽略的一点是：**没有发送字节，不等于发送端已经释放总线。**

在正常、非反相的 UART 配置下，TX 引脚空闲时保持逻辑1。这个电平连接到收发器的 DI 输入。如果 DE 一直为1，驱动器就会持续输出代表逻辑1的差分电平。

以 MAX1482 为例，其发送功能如下：

| DE | DI | Y 输出 | Z 输出 | 发送端状态 |
| --- | --- | --- | --- | --- |
| 1 | 1 | 高 | 低 | 主动驱动逻辑1 |
| 1 | 0 | 低 | 高 | 主动驱动逻辑0 |
| 0 | 任意 | 高阻 | 高阻 | 释放总线 |

这来自[MAX1482/MAX1483 原厂手册](https://www.analog.com/media/en/technical-documentation/data-sheets/MAX1482-MAX1483.pdf)的发送真值表。高阻表示输出不再主动拉高或拉低线路，并不是“输出逻辑0”。

假设主机只查询地址1。从机1开始回复，从机2判断地址不匹配，程序没有发送任何字节。但如果从机2的 DE 仍然为1，它的发送端依旧在维持空闲逻辑1。当从机1发送逻辑0时，两者的输出方向就相反了。

![两台从机 DE 常高时的空闲电平与发送冲突](/image/posts/rs422-full-duplex-polling/02-idle-and-contention.svg)

图2是 DI 逻辑片段示意，不是实测差分波形。发生争用时，总线电压取决于驱动能力、限流、负载和线路条件，不能统一画成某个固定的中间电压。

这也说明，冲突不需要以“两台从机的空闲电平随机相反”为前提。两台正常 UART 都可以空闲为1，只要其中一台开始发送0，而另一台还在驱动1，就可能发生争用。

地址与 DE 解决的是两个相连但不同的问题：**地址选择谁应该回复，DE 控制谁实际上能够驱动回传线。**

<a id="de-polling"></a>

## 3. 用主从轮询安排回复权限

最简单的实现是主从轮询。每台从机有唯一地址，主机一次只发起一个需要立即回复的请求，等待该次回复结束后再查询下一台。

从机收到完整帧后，流程可以写成：

```text
接收完整帧
    ↓
检查帧格式和校验
    ↓
判断地址与命令类型
    ├─ 广播：按广播规则处理，不让所有从机立即回复
    ├─ 本机单播：处理命令，需要应答时开启 DE 回复
    └─ 其他地址：不回复，DE 保持为0
```

发送应答时，仅切换发送驱动，接收器可以继续开启。下面是逻辑伪代码，具体 API 和时序需要按 MCU 与收发器实现：

```c
void send_reply(const uint8_t *data, size_t length)
{
    set_de(1);                  // 使能发送驱动
    wait_driver_enable();       // 满足芯片要求的使能时间

    uart_send(data, length);
    wait_uart_frame_complete(); // 最后一个停止位已经离开发送引脚

    set_de(0);                  // 释放回传线
}
```

这里的“发送完成”必须包含移位寄存器中的最后一位已经发送完毕。DMA 搬运完成或发送数据寄存器为空，都不一定意味着线路上的帧已经结束。应按所用 MCU 对传输完成标志的定义判断，不能只凭固定延时猜测。

DE 拉低后，输出进入高阻也存在器件规定的关闭延迟。安排下一台从机发送时，需要把驱动关闭、线路传播和协议规定的帧间隔纳入交接时间，不能只看软件中两个 GPIO 操作的先后。

在这套四线网络中，主机 DE 可以常高，所有设备的低有效接收使能引脚 `/RE` 可以保持为0。从机的 DE 平时为0，只在获得本次回复权限时拉高。

还要处理一个容易遗漏的边界：**主机超时，不等于迟到的从机已经放弃回复。** 协议需要约定响应时限；超过时限的从机应放弃该次回包，或者使用其他明确的授权规则。否则，主机查询下一台时，上一台才开始回复，仍然可能冲突。

<a id="duplex-capability"></a>

## 4. 严格轮询没有利用全双工能力

如果代码始终执行“请求1、等待回复1、请求2、等待回复2”，那么业务流量确实在交替传输。全双工硬件并不会自动让这些步骤重叠。

但不能由此断言物理链路已经变成半双工。判断区别在于：硬件是否允许发送和接收同时进行，以及协议是否允许应用使用这种能力。

| 概念 | 它回答的问题 | 本例中的含义 |
| --- | --- | --- |
| 全双工 | 两个方向能否同时传输 | 主机下行与从机上行可以同时进行 |
| 一主多从 | 有多少设备以及各自角色 | 一个主机连接多个从机 |
| 轮询 | 由谁安排业务访问顺序 | 主机依次选择从机进行交互 |
| 上行发送权限 | 谁能使用共享回传线 | 同一时刻只允许一个从机驱动 |

“轮询”本身也不必然禁止两个方向重叠。严格的单请求单应答流程是一种轮询实现，是否允许流水处理或并行下发，要由协议另行规定。

<a id="overlap"></a>

## 5. 怎样真正同时发送和接收

要利用四线全双工，可以设计这样的流程：主机先授权从机1上传数据；从机1回传期间，主机通过独立下行线向从机2发送配置。配置帧明确不触发立即回复，从机2先接收并处理，等之后获得回传授权时再报告结果。

此时，主机正在向从机2发送，同时接收从机1的数据。两个方向确实发生了重叠，上行线上也始终最多只有一个从机发送。

![严格轮询与允许上下行重叠的协议时序对比](/image/posts/rs422-full-duplex-polling/03-polling-and-full-duplex.svg)

图3下半部分是一个自定义协议示例，不是标准 Modbus RTU 时序。要采用这种流程，协议和从机固件都必须支持“不立即应答”或“单独授权回传”等机制。

主从机的软件实现也要支持同时收发。例如，发送期间继续通过接收中断或 DMA 接收数据，并准备足够的缓冲，不能让发送流程停掉接收。

如果现有从机固定采用“收到本机请求后立即应答”，主机又无法约束各从机的回复时机，就应按现有协议顺序查询。不能仅因为换成四线接法，就假定设备支持并行事务。

## 6. RS422 和四线 RS485 的边界

严格的 RS-422 每对线上只有一个驱动器，可以连接多个接收器，因此单向一对多广播没有问题。多个从机发送端共用另一对返回线，则引入了多驱动连接与高阻切换要求，通常按四线 RS-485 的方式设计。[ADI 应用指南](https://www.analog.com/en/resources/app-notes/an-960.html)明确区分了这两种总线结构。

RS-485 并不只代表“两线半双工”。它可以采用两线半双工，也可以采用四线全双工；两者都需要避免同一对线上多个驱动器输出相反状态。RS-485 标准也不会自动解析地址、轮询从机或消除冲突。

选择芯片时，必须进一步核对它是否具有发送使能功能：

| 芯片 | 双工能力 | DE 与 /RE | 对共享回传线的意义 |
| --- | --- | --- | --- |
| MAX1482 | 全双工 | 有 | 可以控制从机发送端进入高阻 |
| MAX3490 | 全双工 | 没有 | 不能直接按 DE 分时方案控制其输出 |
| MAX3491 | 全双工 | 有 | 可控制发送输出，但需要按其管脚和电气参数设计 |

[MAX3483 至 MAX3491 原厂手册](https://www.analog.com/media/en/technical-documentation/data-sheets/MAX3483-MAX3491.pdf)的选型表和管脚表明确列出了上述差别。MAX3490 为8引脚，MAX3491 为14引脚，不能当作引脚兼容的替换型号。

这也是为什么“全双工芯片能否一主多从”不能只看产品名称。既要看收发通道是否独立，也要看共享发送通道能否在未获授权时释放总线。

<a id="receive-errors"></a>

## 7. 发送冲突能否解释从机接收错误

从机发送端争用，可以直接解释主机为什么收不到正确回复。但如果现象是“从机连主机下发的命令也接收错误”，还需要检查下行通道，不能仅凭上行争用就确定全部原因。

MAX1482 接收真值表中，接收器开启时 DE 为无关项；DE 本身不负责关闭接收器。不过，收发电路共用芯片电源与地，并不等于电气隔离。争用造成的供电扰动、地噪声或线路耦合，在具体电路中可能间接影响接收，这些是需要测量验证的机制。

排查时，应同时核对出错从机 RX 引脚处的差分信号、相对本地地的共模电压、RO 输出及供电状态。若这些都符合器件要求，再沿 RO 到 MCU 的路径检查 UART 错误标志、接收缓冲和帧解析。仅凭“改了 DE 后恢复正常”，还不足以区分具体的间接影响路径。

<a id="idle-bias"></a>

## 8. 全部发送端关闭后的空闲状态

发送端高阻，不代表整条总线必然处于逻辑1，也不代表差分电压必须为0。空闲状态与终端、外部偏置、接收器输入特性有关。即使所有 DE 都关闭，偏置电阻也可以让总线保持非零差分电压。

MAX1482 手册保证输入开路时 RO 为高，但不能把这项开路保护直接理解为“带终端、差分接近0时也保证为高”。它的保证接收门限为正负200mV，需要按具体电路确定空闲偏置。

例如，假设5V电源、10kΩ上拉、10kΩ下拉，以及一只120Ω终端，忽略输入负载和电阻误差，偏置产生的差分电压约为：

```text
Vdiff = 5V × 120Ω / (10000Ω + 120Ω + 10000Ω)
      ≈ 0.030V
      = 30mV
```

这个数值达不到 MAX1482 的正向200mV保证门限，因此不能把“10kΩ上下拉”作为通用接法。具体阻值还要结合等效终端、输入负载、电源及噪声余量计算。[ADI 的偏置说明](https://www.analog.com/en/resources/app-notes/an-960.html)也区分了传统接收器与具备真失效保护的接收器。

<a id="design-choice"></a>

## 9. 选择与实际通信流程匹配的设计

对于只需要顺序查询的系统，严格轮询通常已经满足业务需求；使用全双工硬件并不要求每次通信都同时收发。

如果希望在从机上传期间继续下发配置或控制数据，就需要把这项并行能力写进协议：下行命令是否立即应答、谁持有上行发送权限、权限何时结束，以及超时后怎样处理，都应有明确规则。

**共享上行线要求从机轮流发送；独立的下行线允许主机同时发送。协议是否使用这种并行能力，决定了四线全双工在系统中能够发挥多大作用。**

## 10. 上板前核对表

把前面的解释落实到固件与测量时，可以逐项记录下表中的结果：

| 检查位置 | 应确认的行为 |
| --- | --- |
| 从机上电与未被寻址时 | DE 保持为 0，发送输出高阻；接收器按设计保持开启 |
| 从机回复开始与结束时 | 先使能驱动并满足使能时间，等最后一个停止位发送完毕后再关闭 DE |
| 两台从机交接时 | 计入驱动关闭延迟、传播时间和协议间隔，避免回传驱动重叠 |
| 主机超时进入下一次查询时 | 旧请求的迟到回复有明确的放弃或重新授权规则 |
| 尝试上下行重叠时 | 下行配置不触发立即回复，接收中断或 DMA 在发送期间继续工作 |
| 全部从机 DE 为 0 时 | 结合实际终端与偏置测量差分电压和 RO，确认符合接收器门限 |
| 出现从机接收错误时 | 分别检查下行差分信号、共模电压、供电、RO 和 MCU 的 UART 状态 |

上表是检查顺序，具体时间与电气限值仍取自实际 MCU、收发器手册和协议约定。
